## 8. Metodologia

### 8.1 Fonte dos feedbacks

Os apontamentos vêm das avaliações publicadas das Sprints 1, 2 e 3, normalizados em uma lista de trabalho com um identificador por item (S1-01 a S3-22), o tipo (documentação, código, GitLab ou informativo) e o critério de correção. A coluna "Feedback" resume cada apontamento sem alterar o seu sentido. Quando uma avaliação posterior já havia confirmado a correção, a confirmação é citada, mas a evidência no repositório foi localizada da mesma forma.

### 8.2 Regra de temporalidade

Só é considerado corrigido o que mudou depois da entrega da sprint avaliada, identificada pelos merges da seção 1.2. Um conteúdo que já existia quando o avaliador fez o apontamento não conta como correção, mesmo que atenda ao critério; é o caso do S1-05. A única exceção é o S1-08: o apontamento anunciava uma cobrança futura, e o avaliador considerou o cabeçalho resolvido no feedback de Gestão da Sprint 1. As datas de cada commit foram conferidas com `git log`, e o commit de cada correção foi localizado com `git log -S`, `-G`, `-L` e `--follow` e confirmado com `git show`.

### 8.3 Critério para itens de código

Um item de código só é "Corrigido" quando o comportamento está implementado e há teste executado e aprovado nesta revisão. A exceção é o S3-11, verificado por análise estática do grafo de migrações: das 12 revisões, uma é a base e uma é a única versão final, sem migrações de merge. A execução de `alembic upgrade head` em banco novo não foi verificada nesta revisão, porque exigiria um PostgreSQL local.

### 8.4 Itens de GitLab

Os itens S2-15, S2-18 e S3-22 dependem do estado do GitLab (issues, labels e tags). Eles foram verificados apenas pela documentação do repositório e pelo git local, incluindo a listagem de tags do remoto com `git ls-remote --tags origin`. As issues, as labels e os responsáveis não foram consultados na interface nem na API do GitLab.
